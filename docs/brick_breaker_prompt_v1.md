## 1. Purpose

This document establishes a standardized sequence of prompts, verification checkpoints, evidence requirements, and intervention rules for developing the same Brick Breaker application using two AI-assisted development environments.

- **Assignment 4:** ChatGPT.
- **Assignment 5:** Grok within Cursor.

The protocol is designed to make the two development runs as comparable, repeatable, auditable, and evidence-based as practical.

The authoritative implementation requirements are defined in `Brick_Breaker_SRS_v1.0.md`. This protocol does not replace, amend, or relax that specification.

No implementation has been generated, executed, or validated by preparing this protocol.

## 2. Experimental Control Rules

The following rules are mandatory for both assignments.

**EXP-01 — Common specification.** Both AI systems SHALL receive the same frozen `Brick_Breaker_SRS_v1.0.md`, including its constants, API contracts, collision rules, 28 tests, 10 browser checks, and interpretation rules.

**EXP-02 — Common prompts.** The checkpoint prompts in this protocol SHALL be submitted unchanged wherever practical. Environment-specific context and observed results SHALL be supplied in separate standardized evidence fields, not by rewriting the core prompts.

**EXP-03 — Independent implementations.** ChatGPT and Grok SHALL work in separate implementation directories. Code generated by one AI SHALL NOT be provided to the other during development.

**EXP-04 — Baseline preservation.** The complete implementation produced at CP-02 SHALL be preserved before any repairs or corrective edits. The baseline SHALL remain available for later inspection.

**EXP-05 — Test isolation.** The independent unit-test source, hidden assertions, and any validation reference implementation SHALL NOT be disclosed to either AI before the CP-02 baseline has been generated and preserved. The test harness SHALL remain independent throughout the experiment.

**EXP-06 — Evidence-based reporting.** Neither AI nor the human evaluator SHALL report a test as passed unless it has actually been executed and its result observed.

**EXP-07 — Repair limit.** A maximum of two AI repair attempts SHALL be allowed for each failed checkpoint. An attempt counts when the AI is authorized to make corrective code changes, regardless of whether the changes succeed.

**EXP-08 — Frozen requirements and tests.** The SRS, independent test fixtures, and frozen assertions SHALL NOT be altered to make either implementation pass. Any suspected specification or test error SHALL be logged and handled outside the active comparison.

**EXP-09 — Audit trail.** Elapsed time, prompts, responses, implementation snapshots, commands, test outcomes, repairs, and human interventions SHALL be recorded.

**EXP-10 — Actor attribution.** Every consequential action SHALL be identified as AI-performed, human-performed, or independently executed by an evaluation tool.

**EXP-11 — Equivalent evaluation.** Both implementations SHALL be evaluated using the same test harness version, assertions, test environment, and pass/fail rules.

**EXP-12 — Honest limitations.** An AI system SHALL explicitly disclose when it cannot access files, execute commands, operate a browser, or observe a test. It SHALL NOT fabricate execution or inspection results.

**EXP-13 — No cross-run contamination.** During implementation, neither AI SHALL receive the other implementation's source code, prompts containing its repair solutions, internal debugging information, or test outcomes.

**EXP-14 — No unrecorded repairs.** After the CP-02 snapshot, no code changes SHALL occur without an identified checkpoint, actor, reason, and recorded before/after snapshot.

**EXP-15 — Fixed checkpoint order.** The prescribed checkpoint order SHALL be maintained, except when CP-09 is explicitly invoked to resolve a blocker. A blocked checkpoint SHALL not silently disappear from the record.

## 3. Standardized Environment and Directory Structure

### 3.1 Implementation Directories

The experiment SHALL maintain two independent working directories:

```
Brick_Breaker_Experiment/
├── Assignment_4_ChatGPT/
│   ├── implementation/
│   └── evidence/
├── Assignment_5_Grok_Cursor/
│   ├── implementation/
│   └── evidence/
└── shared_evaluation/
```

Only these four files SHALL be delivered as the game implementation:

```
index.html
game.js
gameLogic.js
package.json
```

The `package.json` SHALL contain `"type": "module"`.

The experiment directories, evidence files, snapshots, SRS, protocol, and independent test harness are external to the four-file game deliverable.

No tests, scripts, generated artifacts, or additional configuration files SHALL be added to an implementation's final submission directory.

### 3.2 Required Snapshot Names

The experimenter SHALL preserve snapshots using the following labels:

| Snapshot           | Meaning                                                       |
| ------------------ | ------------------------------------------------------------- |
| `CP02_BASELINE`    | Original complete AI-generated implementation, before repairs |
| `CP06_REPAIR_01`   | State after first AI repair attempt                           |
| `CP06_REPAIR_02`   | State after second AI repair attempt                          |
| `FINAL_SUBMISSION` | Implementation at the end of the run                          |

If a checkpoint-specific repair occurs outside CP-06, its snapshot SHALL include the checkpoint identifier and repair number, for example `CP04_REPAIR_01`.

Snapshots MAY be implemented as immutable directory copies, archives, or version-control commits. They SHALL be maintained outside the four-file deliverable directory.

For each snapshot, record a SHA-256 checksum of each implementation file when hashing tools are available.

### 3.3 Environment Consistency

Before beginning development, the human experimenter SHALL record:

- Operating system and version.
- Browser and version.
- JavaScript runtime and version, if used.
- Code editor and version.
- AI product and model name, as displayed.
- Local serving method and command.
- Test-harness version or checksum.
- SRS version or checksum.
- Protocol version.
- Date and time of experiment execution.

The same environment SHOULD be used for both assignments. Any unavoidable differences SHALL be documented and considered during comparison.

### 3.4 Tool-Access Differences

ChatGPT and Grok within Cursor may have different capabilities for file editing, terminal execution, and browser access.

For comparability:

- An AI with the necessary tools MAY directly perform an authorized checkpoint action.
- An AI without those tools SHALL provide the exact commands or instructions needed for the human to perform the action.
- The human SHALL execute only the requested evaluation operation and return the actual output.
- Human execution SHALL be logged separately from AI execution.
- Inability to operate a tool SHALL not be reported as successful execution.

The same checkpoint requirements and completion gates SHALL apply in both cases.

## 4. Standard Checkpoint Execution Procedure

The experimenter SHALL use the following sequence for every checkpoint.

1. Record the checkpoint start time.
2. Submit its exact standardized prompt.
3. Provide the required SRS or evidence artifacts according to the checkpoint's access rules.
4. Record the AI response and any tool actions.
5. Perform the checkpoint's authorized verification activities.
6. Save logs, outputs, and screenshots where applicable.
7. Evaluate the completion gate.
8. Record PASS, FAIL, or BLOCKED.
9. Record the checkpoint end time and elapsed time.
10. Advance only when the gate permits, or invoke the documented repair/recovery procedure.

A checkpoint that has not been executed SHALL be marked NOT RUN rather than PASS.

### 4.1 Standard Evidence Envelope

When a checkpoint requires observations from an earlier checkpoint, the experimenter SHALL attach them after the unchanged checkpoint prompt using this format:

```
BEGIN CHECKPOINT EVIDENCE

Experiment ID:
Checkpoint ID:
Evidence source:
Performed by:
Execution timestamp:
Execution environment:
Command or action:
Observed output:
Error messages:
Related test IDs:
Snapshot ID:
Additional notes:

END CHECKPOINT EVIDENCE
```

Fields with no applicable information SHALL contain `N/A`.

The experimenter SHALL provide actual evidence, not guessed or reconstructed outputs.

### 4.2 Standard AI Response Requirements

Each checkpoint response SHALL distinguish:

- Actions actually performed.
- Actions proposed but not performed.
- Observed results.
- Unverified expectations.
- Identified defects or risks.
- Evidence supporting the conclusion.
- Any required human intervention.

When required evidence is unavailable, the AI SHALL state the limitation.

# 5. Standardized Checkpoint Prompts

## CP-00 — Read and Summarize the SRS

**Objective:** Confirm requirements comprehension before any implementation activity.

**Permitted:** Reading, summarizing, requirement analysis, and identifying ambiguities.

**Prohibited:** Generating implementation code, creating implementation files, running the application, or modifying the SRS.

### Exact prompt — CP-00

```
CHECKPOINT CP-00 — SRS COMPREHENSION

You are participating in a controlled university
software-development experiment.

Your task is to read and analyze the attached
Brick_Breaker_SRS_v1.0.md.

Do not write, generate, edit, or execute any game code.

Treat the SRS as the authoritative and frozen
requirements baseline.

Produce the following:

1. A concise summary of the game's purpose and scope.

2. A list of the four required implementation files
   and their responsibilities.

3. A summary of the required public API:
   createInitialState()
   updateGame(state,input,dt)
   resetGame()

4. A summary of the exact initial state, constants,
   coordinate system, scoring, lives, and statuses.

5. A summary of input handling, pause behavior,
   restart behavior, and terminal-state behavior.

6. A summary of swept collision detection,
   chronological event ordering, corner collisions,
   simultaneous contacts, reflection rules,
   and bottom-exit semantics.

7. A list of the 12 functional requirements,
   BRICK-FR-01 through BRICK-FR-12.

8. A summary of the 28 pure-logic tests and
   10 browser acceptance checks.

9. Any ambiguities or implementation risks,
   with references to the relevant SRS sections.

Do not invent new requirements.

Do not reinterpret an explicit requirement.

Do not propose code yet.

Clearly distinguish stated requirements from
your own observations or interpretations.

End your response with:

CP-00 STATUS: REQUIREMENTS REVIEW COMPLETE

If you cannot read the complete SRS, report the
missing information and do not claim completion.
```

### Expected Evidence

- Full AI response.
- Confirmation that the complete SRS was accessible.
- Correct identification of the three API functions.
- Correct identification of the four deliverables.
- Coverage of the 12 functional requirements.
- Recognition of the collision, pause, terminal, determinism, and immutability rules.
- List of identified ambiguities or risks.
- Confirmation that no implementation files were generated or modified.

### Completion Gate

**PASS:** Requirements summary is materially accurate, includes all required topics, and no code was written.

**FAIL:** The response materially misstates mandatory requirements or generates implementation code.

**BLOCKED:** The complete SRS cannot be accessed or reviewed.

The checkpoint SHALL NOT proceed as PASS merely because the AI reports that it understands the specification.

## CP-06 — Diagnose, Repair, and Retest Observed Defects

**Objective:** Correct verified defects under a fixed repair budget and measure the effectiveness of each repair attempt.

**Permitted:** Reviewing diagnostic evidence, changing implementation code, and rerunning the same frozen tests.

**Prohibited:** Editing the SRS, weakening tests, introducing extra deliverable files, or exceeding the repair budget.

### Repair Budget

For each failed checkpoint eligible for repair:

- Attempt 1: Maximum one authorized AI correction cycle.
- Attempt 2: Maximum one additional authorized AI correction cycle.
- No third AI repair attempt is permitted.

A repair cycle may contain changes to multiple implementation files, but all changes made in that cycle SHALL be treated as one recorded attempt.

Diagnostic discussion without source modification does not itself count as a repair attempt.

Each authorized AI code-editing cycle SHALL count even if the edit is incomplete, ineffective, or cannot be executed.

### Exact prompt — CP-06

```
CHECKPOINT CP-06 — CONTROLLED DEFECT REPAIR

The implementation has completed
baseline generation and initial verification.

You are authorized to diagnose and repair
observed defects using the evidence provided.

Follow the frozen
Brick_Breaker_SRS_v1.0.md.

Do not modify the SRS.

Do not modify independent test assertions,
fixtures, or reference implementations.

Do not add external runtime libraries.

Do not introduce extra implementation files.

You have a maximum of two AI repair
attempts for the failed checkpoint.

The experimenter will identify the current
attempt number and provide observed
failure evidence.

Use only supported observations and
source-code inspection to determine causes.

Do not invent test results.

Before modifying code, report:

1. The failed checkpoint and test IDs.
2. The observed symptoms.
3. The most likely root causes.
4. The relevant SRS requirements.
5. The specific files requiring changes.
6. The proposed minimal corrections.

Then make only the code changes necessary
to address supported defects.

Preserve all required public APIs,
constants, and state invariants.

Do not weaken unrelated behavior.

After the changes:

1. Identify every modified file.
2. Summarize the actual changes.
3. State the current repair attempt number.
4. Provide the resulting source snapshot.
5. Run the same frozen tests if authorized
   execution tools are available.
6. Otherwise request human execution
   and report the supplied results.
7. Record the exact outcomes of retesting.
8. Identify any remaining failures.
9. State whether the repair budget remains.

Do not report success without test evidence.

Do not perform an additional repair
without a separately authorized attempt.

End your response with:

CP-06 STATUS: REPAIR ATTEMPT RECORDED
```

### Required Repair Evidence Envelope

For each invocation, the human experimenter SHALL provide:

```
Failed checkpoint:
Repair attempt number: 1 or 2
Current implementation snapshot:
Observed failed test IDs:
Observed error messages:
Relevant execution output:
Previously attempted repairs:
Remaining authorized attempts:
```

### Repair and Retest Procedure

For each authorized attempt:

1. Preserve the pre-repair state.
2. Record the attempt start time.
3. Provide the exact failed-test evidence to the AI.
4. Record the AI's diagnosis.
5. Authorize one correction cycle.
6. Preserve the resulting implementation snapshot.
7. Run the same frozen harness or checkpoint verification.
8. Record all passing and failing results.
9. Record attempt completion time.
10. Decide whether another attempt is permitted.

Previously passing tests SHALL be rerun to detect regressions whenever the affected checkpoint requires test execution.

If the first repair passes all required checks, the second attempt SHALL not be used.

If two attempts fail, the implementation SHALL retain its unresolved defect status.

The experimenter SHALL NOT silently provide additional hints, rewrite tests, or permit a third correction cycle.

### Expected Evidence

- Original defect IDs and observations.
- Repair attempt number.
- AI root-cause explanation.
- Changed-file inventory.
- Before/after source snapshots.
- Diff or equivalent change record.
- Full retest output.
- Updated test totals.
- Regression findings.
- Remaining defect list.
- Repair start and end timestamps.

### Completion Gate

**PASS:** All failures assigned to the checkpoint have been corrected and verified without violating the SRS.

**FAIL:** Failures remain after the allowed repair attempts, or a repair introduces unresolved regressions.

**BLOCKED:** A documented environmental problem prevents diagnosis or retesting.

A failed CP-06 SHALL remain part of the final record. It SHALL not prevent the experiment from documenting later checkpoints if they can still be meaningfully executed.

# 6. Checkpoint Sequence and Decision Rules

## 6.1 Standard Sequence

| Order    | Checkpoint | Primary activity                    | Code changes permitted                                            |
| -------- | ---------- | ----------------------------------- | ----------------------------------------------------------------- |
| 1        | CP-00      | Requirements comprehension          | No                                                                |
| 2        | CP-01      | Implementation planning             | No                                                                |
| 3        | CP-02      | Complete baseline generation        | Yes — initial generation only                                     |
| 4        | CP-03      | Static compliance review            | No                                                                |
| 5        | CP-04      | Initial runtime launch              | No                                                                |
| 6        | CP-05      | Independent first-run logic tests   | No                                                                |
| 7        | CP-06      | Controlled defect repair and retest | Yes — maximum 2 attempts per failed checkpoint                    |
| 8        | CP-07      | Manual browser acceptance           | No, except separately authorized controlled repairs               |
| 9        | CP-08      | Final engineering report            | No                                                                |
| Optional | CP-09      | Blocker recovery                    | Environmental changes only, unless separately counted as a repair |

## 6.2 Advancement Rules

A checkpoint SHALL advance normally when its completion gate passes.

When a checkpoint fails:

- Preserve the actual failed result.
- Determine whether the failure is a process failure or an implementation defect.
- Use the controlled repair procedure only when source changes are necessary and authorized.
- Do not repeat a checkpoint as though the previous failure never occurred.
- Retain the original result and every retest result.

For CP-03, completion of the review can pass even when noncompliance is detected.

For CP-05 and CP-07, test failures SHALL be recorded independently of whether their required execution/reporting activity was completed.

CP-04 and CP-05 first-run evidence SHALL be captured before repair activity whenever execution is possible.

If a blocked checkpoint prevents subsequent evaluation, record the dependency and use CP-09. If recovery fails, continue only with meaningful, feasible checkpoints and mark unavailable results BLOCKED or NOT RUN as appropriate.

## 6.3 Repair Attempt Accounting

The experiment SHALL maintain an attempt ledger.

| Failed checkpoint | Attempt 1 | Attempt 2 | Remaining | Final status |
| ----------------- | --------- | --------- | --------- | ------------ |
| CP-04             | Not used  | Not used  | 2         | Pending      |
| CP-05             | Not used  | Not used  | 2         | Pending      |
| CP-07             | Not used  | Not used  | 2         | Pending      |

Other checkpoints MAY receive documented correction handling when necessary, subject to the same maximum.

An attempt SHALL be counted against the failed checkpoint that authorized it. If one correction also resolves another checkpoint's defect, that secondary effect SHALL be documented rather than counted as an additional attempt.

Repeating unchanged tests does not consume a repair attempt. Modifying source code in response to failed verification does.

The experimenter SHALL record whether human-authored corrective code was introduced; such interventions SHALL not be disguised as AI repair success.

# 9. Comparative Analysis Procedure

## 9.1 Comparison Prerequisites

After both assignments are completed, the experimenter SHALL verify:

- The same SRS was used.
- The same checkpoint prompts were used.
- The same independent test suite was used.
- The same test assertions were applied.
- The same environment was used or differences were documented.
- The implementations remained isolated.
- Original baselines were preserved.
- All repairs and human interventions were logged.
- Both final reports distinguish executed results from assumptions.

## 9.2 Comparative Metrics

| Metric                           | Assignment 4: ChatGPT | Assignment 5: Grok within Cursor |
| -------------------------------- | --------------------- | -------------------------------- |
| Baseline generation time         | Not measured          | Not measured                     |
| Total development time           | Not measured          | Not measured                     |
| Prompt count                     | Not recorded          | Not recorded                     |
| Baseline tests passed / 28       | Not run               | Not run                          |
| Final tests passed / 28          | Not run               | Not run                          |
| Browser checks passed / 10       | Not run               | Not run                          |
| AI repair attempts               | Not recorded          | Not recorded                     |

| Defects remaining                | Not assessed          | Not assessed                     |
| Overall required-check pass rate | Not measured          | Not measured                     |
| Final conformance                | Not assessed          | Not assessed                     |

## 9.3 Metric Formulas

**Logic-test pass rate:**

[\
P_L=\frac{N\_{\text{logic passed}}}{28}\times100%\
]

**Browser acceptance pass rate:**

[\
P_B=\frac{N\_{\text{browser passed}}}{10}\times100%\
]

**Overall required-check pass rate:**

[\
P_O=\frac{N\_{\text{all passed}}}{38}\times100%\
]

For these metrics, failed, blocked, and not-run checks remain in the denominator.

The experimenter SHALL additionally report how many checks were actually executed so that a low pass rate caused by missing evidence is distinguishable from one caused by observed software defects.

## 9.4 Threats to Validity

The final comparative report SHALL discuss relevant threats to validity, including:

- Different AI model capabilities or versions.
- Different file-system, terminal, or browser tool access.
- Differences in context retention.
- Differences in editor integration.
- Human transcription or intervention.
- Differences in wall-clock execution conditions.
- Potential test or prompt leakage.
- Unequal recovery guidance.
- Incomplete test execution.
- Unresolved specification interpretations.
- Nonrepeatable browser observations.
- Small sample size from one development run per AI.

The experiment SHALL not treat differences in total interaction time as pure model-performance differences without accounting for environment and human operational overhead.

## 9.5 Interpretation of Results

The comparison SHALL distinguish initial implementation quality from post-repair quality.

Specifically, the report SHOULD analyze:

1. **First-generation compliance:** How many tests the original CP-02 baseline passed.
2. **Repair effectiveness:** How many defects were corrected within the permitted repair budget.
3. **Browser usability:** Which user-visible checks passed.
4. **Development efficiency:** Recorded time, prompt count, and intervention count.
5. **Specification fidelity:** Whether either implementation introduced prohibited behavior.
6. **Engineering reliability:** Whether modifications created regressions or unresolved defects.

A higher pass rate does not automatically establish lower development cost, and shorter development time does not automatically establish greater requirements compliance.

- Original checkpoint prompt.

- Original checkpoint prompts.
